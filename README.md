# Call Me Maybe

## Description

**Call Me Maybe** is a function-calling project developed as part of the 42 curriculum.

The goal is to use a Large Language Model (LLM) to determine which function should be called from a natural-language request and produce a valid JSON object containing the selected function and its parameters.

Unlike unrestricted text generation, this project uses **constrained decoding** to control the tokens generated by the model according to the expected JSON structure.

The program:

* loads function definitions from a JSON file;
* loads user prompts from another JSON file;
* uses an LLM to select the most appropriate function;
* extracts the required parameters from the user's prompt;
* generates the final function call as JSON;
* writes the results to an output JSON file.

# Algorithm Explanation

The project implements **constrained decoding** instead of unrestricted text generation.

The LLM is used to select the most appropriate function from the available function definitions. During generation, the decoder restricts the tokens that the model is allowed to produce according to the current state of the expected JSON structure.

The expected structure is:

```json
{
    "name": "...",
    "parameters": {
        ...
    }
}
```

The decoding process is divided into several stages:

1. Generate the opening `{`.
2. Generate the `"name"` key.
3. Generate the selected function name.
4. Generate the `"parameters"` key.
5. Generate or extract the required parameters.
6. Generate the closing `}`.
7. Return the resulting function call.

The decoder uses a state machine to determine which tokens are valid at each stage.

This prevents the model from freely generating arbitrary JSON syntax and keeps the generated structure consistent with the expected format.

# Parameter Extraction

Function selection is performed using the LLM, while parameter extraction is handled separately using deterministic Python logic.

This hybrid approach improves reliability because parameter extraction does not depend entirely on the model's generated text.

The parameter extractor handles several common natural-language patterns, including:

* integers;
* floating-point numbers;
* booleans;
* quoted strings;
* names;
* regular expressions;
* replacement strings;
* Unix file paths;
* Windows file paths;
* file encodings;
* database names;
* templates.

For example:

```text
Replace all numbers in "Hello 34 I'm 233 years old" with NUMBERS
```

produces:

```json
{
    "name": "fn_substitute_string_with_regex",
    "parameters": {
        "source_string": "Hello 34 I'm 233 years old",
        "regex": "\\d+",
        "replacement": "NUMBERS"
    }
}
```

# Design Decisions

## State Machine

A finite-state machine is used to represent the expected JSON structure.

This makes the constrained decoder easier to reason about and prevents invalid token sequences from being generated.

## Hybrid Architecture

The project separates the two main responsibilities:

```text
LLM
 ↓
Function selection

Python heuristics
 ↓
Parameter extraction
```

The LLM is responsible for understanding the user's request and selecting the appropriate function.

Python-based extraction handles the parameters deterministically.

## Pydantic Validation

Function definitions and function-calling tests are represented using Pydantic models.

This validates the input data before it is used by the decoder.

Invalid definitions or malformed input are detected during parsing instead of being silently accepted.

## Error Handling

The parser handles common input errors such as:

* missing files;
* invalid JSON;
* invalid JSON structure;
* invalid function definitions;
* invalid parameter types.

Errors are reported without exposing an unhandled traceback to the user.

# Performance Analysis

The implementation focuses on three objectives.

## Accuracy

The constrained decoder correctly selects functions for the provided test sets.

The parameter extractor handles numeric, boolean, string, path, encoding, database and template parameters.

## Speed

The project remains within the required execution time.

JSON parsing and deterministic parameter extraction introduce negligible overhead compared with LLM inference.

## Reliability

The constrained decoding mechanism restricts generation to the expected JSON structure.

Input validation and error handling also prevent common invalid-input situations from terminating the program unexpectedly.

# Challenges Faced

Several challenges were encountered during development.

## Constrained Decoding

Implementing token filtering while preserving valid model predictions required careful state management.

The decoder must know which tokens are valid depending on its current position in the JSON structure.

## Token Vocabulary

The tokenizer vocabulary had to be loaded and indexed so that the decoder could efficiently determine which tokens were allowed during generation.

## Parameter Extraction

Natural-language prompts can express the same information in many different ways.

Specific extraction strategies were therefore implemented for:

* numbers;
* integers;
* booleans;
* quoted strings;
* names;
* regular expressions;
* replacement values;
* file paths;
* encodings;
* database names;
* templates.

## Robustness

The parser and execution flow were improved to handle invalid input without unexpectedly terminating the program.

Special attention was given to malformed JSON, missing files, invalid Pydantic models and parameter extraction failures.
